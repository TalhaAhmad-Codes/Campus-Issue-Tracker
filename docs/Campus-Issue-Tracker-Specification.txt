CAMPUS ISSUE TRACKER — PROJECT SPECIFICATION
================================================

Document Purpose
----------------
This document is the complete project specification for a beginner-to-intermediate MERN stack project called "Campus Issue Tracker".

It is intended to be provided to an AI coding assistant as the primary project context and development reference.

The project should remain intentionally manageable. Do not introduce enterprise-level architecture, unnecessary abstractions, microservices, CQRS, event sourcing, or other advanced patterns unless explicitly requested.


1. PROJECT OVERVIEW
===================

Project Name:
Campus Issue Tracker

Project Type:
Campus/university issue reporting and management web application.

Primary Goal:
Allow students to report campus problems and allow staff/admins to track, assign, process, resolve, and close those issues through a centralized web application.

Example:
A student notices that a projector in Computer Lab 3 is not working. The student creates an issue containing its title, description, category, location, and priority. An administrator can assign it to an appropriate staff member. The staff member works on it and updates its status. The student can follow the progress until the issue is resolved and closed.

The application should feel like a small real-world service-desk/ticketing system, but it must remain simple enough for a beginner/intermediate MERN learner to complete within a reasonable period.


2. TARGET USERS AND ROLES
==========================

There are three primary roles:

1. Student
2. Staff
3. Admin

STUDENT
-------
Students can:
- Register and log in.
- View their own reported issues.
- Create new issues.
- View issue details.
- Add comments to their issues.
- View issue status and progress/history.
- Receive in-app notifications when important changes occur.
- Edit/delete their own issues only where the business rules permit.

STAFF
-----
Staff members can:
- Log in.
- View issues assigned to them.
- View relevant issue details.
- Add comments.
- Update issue status according to permitted workflow.
- Mark work as completed/resolved.
- View their workload.
- Receive notifications about assignments and important updates.

ADMIN
-----
Admins can:
- View all issues.
- Assign issues to staff.
- Change issue priority.
- Manage users/staff.
- Manage issue categories.
- View system-wide statistics.
- View all issue history/comments where appropriate.
- Manage or moderate issues.
- Perform administrative operations.

IMPORTANT:
Use role-based authorization on the backend. Never rely only on frontend route protection for security.


3. CORE FUNCTIONAL REQUIREMENTS
================================

3.1 Authentication
------------------

Implement:
- User registration.
- User login.
- User logout.
- JWT-based authentication.
- Password hashing.
- Current-user endpoint.
- Protected API routes.
- Role-based authorization.

Initial registration should create Student users by default.

Admin-created staff/admin accounts can be added later.

Suggested endpoints:

POST   /api/auth/register
POST   /api/auth/login
GET    /api/auth/me


3.2 User Management
-------------------

User properties should approximately include:

- id
- name
- email
- passwordHash
- role
- isActive
- createdAt
- updatedAt

Roles:
- Student
- Staff
- Admin

Admins should be able to view/manage users.

Do not allow ordinary users to arbitrarily change their role.


3.3 Issue Management
--------------------

Issue is the primary entity.

An issue should approximately contain:

- id
- title
- description
- categoryId
- location
- priority
- status
- reportedBy
- assignedTo
- createdAt
- updatedAt
- resolvedAt
- closedAt

Issue title:
Short description of the problem.

Issue description:
Detailed explanation of the problem.

Category:
Reference to a Category.

Location:
Should contain practical campus location information.

Example:

Building: Computer Science Block
Floor: 2
Room: Lab 3
Additional Details: Near the entrance

Priority:
- Low
- Medium
- High
- Critical

Status:
- Open
- Assigned
- In Progress
- Resolved
- Closed
- Rejected


3.4 Issue Workflow
------------------

Default workflow:

Open
  ->
Assigned
  ->
In Progress
  ->
Resolved
  ->
Closed

Rejected can be used when an issue is invalid, inappropriate, duplicate, or otherwise not actionable.

Do not implement a complicated workflow engine.

The backend should validate allowed status transitions.

Example:

Open -> Assigned
Assigned -> In Progress
In Progress -> Resolved
Resolved -> Closed

The exact transition rules may be adjusted during implementation, but invalid arbitrary transitions should not be accepted blindly.


3.5 Issue Assignment
--------------------

Admins can assign an issue to a Staff member.

Example:

Issue:
Projector not working

Assigned Staff:
Ahmed Khan

The assigned staff member should then see the issue in their dashboard.

When assignment occurs:
- Store assignedTo.
- Record the change in issue history.
- Generate an in-app notification for the staff member.


3.6 Categories
--------------

Initial categories may include:

- IT
- Electrical
- Furniture
- Cleaning
- Plumbing
- Security
- Facilities
- Other

Categories should be stored in their own collection/table rather than hardcoded into every issue.

Admins can:
- Create categories.
- Edit categories.
- Deactivate/remove categories where appropriate.

Avoid physically deleting categories if doing so would break historical issue references. Prefer an isActive field when appropriate.


3.7 Comments
------------

Users should be able to add comments to issues where permitted.

A comment should approximately contain:

- id
- issueId
- authorId
- content
- createdAt
- updatedAt

Example conversation:

Student:
"The projector is still not working."

Staff:
"I checked the HDMI cable. I will replace it tomorrow."

Comments should be associated with the issue.


3.8 Issue History / Activity Log
--------------------------------

Maintain a simple activity/history collection.

Record important events such as:

- Issue created.
- Issue assigned.
- Assignment changed.
- Priority changed.
- Status changed.
- Comment added.
- Issue resolved.
- Issue closed.
- Issue rejected.

Example:

10:30 AM — Issue created by Ali.
10:45 AM — Assigned to Ahmed.
11:20 AM — Status changed to In Progress.
02:10 PM — Comment added by Ahmed.
Next day — Status changed to Resolved.

Suggested history fields:

- id
- issueId
- actorId
- actionType
- oldValue
- newValue
- description
- createdAt

Keep the activity system simple. It is an audit/history feature, not a full event-sourcing system.


3.9 Notifications
------------------

Use simple in-app notifications.

Examples:

- "Your issue #1042 has been assigned to Ahmed."
- "Issue #1042 is now In Progress."
- "Your issue #1042 has been resolved."

Suggested fields:

- id
- recipientId
- issueId (optional)
- type
- message
- isRead
- createdAt

Real-time WebSocket/socket.io notifications are OPTIONAL and should be implemented only after the core application works.


3.10 Search, Filtering, and Pagination
---------------------------------------

Issues should support:

Search:
- Title
- Description
- Location

Filters:
- Status
- Priority
- Category
- Assigned Staff
- Date range

Pagination:
- page
- limit

Example:

GET /api/issues?search=projector&status=InProgress&priority=High&page=1&limit=10

The backend should perform filtering rather than downloading all issues to the frontend and filtering everything there.


3.11 Dashboards
---------------

STUDENT DASHBOARD
-----------------
Show:
- Total reported issues.
- Open issues.
- In-progress issues.
- Resolved issues.
- Recent issues.
- Quick action to create an issue.

STAFF DASHBOARD
---------------
Show:
- Total assigned issues.
- Open assigned issues.
- In-progress issues.
- Resolved issues.
- High/Critical priority issues.
- Recent assigned issues.

ADMIN DASHBOARD
---------------
Show:
- Total issues.
- Open issues.
- Assigned issues.
- In-progress issues.
- Resolved issues.
- Critical issues.
- Issue counts by category.
- Optional issue counts by status/priority.
- Recent issues.

Charts are optional and should not delay core functionality.


3.12 File Attachments — OPTIONAL
--------------------------------

Users may eventually attach images to issues.

Example:
A student uploads a photograph of a leaking pipe.

Do NOT implement file uploads during the initial MVP unless explicitly requested.

If implemented later, use an appropriate file/object storage solution rather than storing large files directly in MongoDB documents.


4. NON-FUNCTIONAL REQUIREMENTS
===============================

The application should be:

- Responsive.
- Usable on desktop and mobile.
- Secure against basic authentication/authorization mistakes.
- Easy to understand.
- Maintainable.
- Beginner-friendly.
- API-driven.
- Modular without overengineering.

Use clear naming and consistent conventions.

Validate input on the backend even if frontend validation exists.

Return consistent API responses and HTTP status codes.

Do not expose password hashes or sensitive authentication data.

  ->

  ->

      |
      v
Issue Route
      |
      v
Issue Controller
      |

9. AUTHORIZATION RULES
======================

Student:
- Can create issues.
- Can view their own issues.
- Can comment on permitted issues.
- Cannot assign issues.
- Cannot manage categories.
- Cannot manage users.
- Cannot change their own role.

Staff:
- Can view issues assigned to them.
- Can update permitted fields/statuses of assigned issues.
- Can comment on assigned issues.
- Cannot manage users/categories unless explicitly granted permission.

Admin:
- Full issue management.
- Assign issues.
- Change priority.
- Manage categories.
- Manage users.
- View system-wide information.

Backend must enforce these rules.

12. VALIDATION
==============

Validate both frontend and backend.

Examples:

Registration:
- Name required.
- Valid email required.
- Password required.
- Password minimum length.

Issue:
- Title required.
- Description required.
- Category required.
- Location required.
- Priority must be a valid enum/value.

Comment:
- Content required.
- Prevent empty/whitespace-only comments.

Use appropriate HTTP status codes:

200 — successful request
201 — resource created
400 — invalid request
401 — unauthenticated
403 — unauthorized
404 — resource not found
409 — conflict
422 — validation error if desired
500 — unexpected server error


13. ERROR HANDLING
==================

Backend should have centralized error-handling middleware.

Do not expose raw stack traces to users in production.

Errors should have a predictable shape, for example:

{
  "success": false,
  "message": "Issue not found",
  "errors": []
}

Successful responses can follow a similarly consistent structure if desired.


14. SECURITY REQUIREMENTS
=========================

Minimum security requirements:

- Hash passwords.
- Never return passwordHash.
- Validate and sanitize input.
- Protect authenticated endpoints.
- Enforce authorization on backend.
- Use environment variables for secrets.
- Do not commit .env files.
- Configure appropriate CORS.
- Use secure JWT handling.
- Avoid trusting client-provided user IDs for authorization decisions.
- Validate MongoDB ObjectIds.
- Prevent users from modifying resources they do not own unless their role permits it.

For production, consider:
- HTTP security headers.
- Rate limiting.
- Secure cookies if cookie-based JWT storage is chosen.
- CSRF protection where applicable.
